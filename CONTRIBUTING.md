# Contributing

Keep the release focused on the interpreter, its supported host operations, the three Flow actions, and their property editors. Do not add research probes, downloaded vendor bundles, org-local state, generated bytecode, customer records, or credentials.

1. Read [development](docs/development.md), [architecture](docs/architecture.md), and [security](SECURITY.md).
2. Create a branch. Keep changes scoped and preserve the published action contract unless a versioned migration is documented.
3. Add behavioral tests for the changed paths. Include empty values, failure behavior, bulk isolation, and budget boundaries where relevant. Avoid tests that only repeat the implementation.
4. Run local checks and validate Apex plus the integration Flows in a fresh scratch org.
5. Update the admin guide and examples when behavior changes. Include validation evidence and limitations in the pull request.

Do not relax a budget or introduce a native accelerator solely to make one library appear compatible. Any new host capability requires an explicit scope, security review, and tests proving the boundary.
